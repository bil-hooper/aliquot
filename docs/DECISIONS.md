# Decisions log

Every architecture call, with a date and one line of reasoning (§8). Newest first.

## 2026-10-04 — Sprint 3 pulled forward: GPU-picking spike

- **Why now, not Sprint 3 on schedule:** picking lives in the exact same `Scene.tsx` the renderer spike already built, and the plan itself (§3.2) treats GPU picking as a required technique for this scene, not a separate concern — doing it right after the renderer spike, while that code is still fresh, beat waiting for the calendar to say "Sprint 3."
- **`web/src/scene/PickingLayer.tsx`** builds a second, invisible `THREE.Scene` containing one `InstancedMesh` per shell (independent geometry/material from the visible `ShellInstances` — deliberately not shared, so this new, unproven path can't risk the already-working visual layer), where every instance's color encodes `globalId + 1` as an 8-bit-per-channel RGB value (0 reserved for "no hit," headroom for ~16.7M nodes). Hover/click calls `camera.setViewOffset(canvasWidth, canvasHeight, pixelX, pixelY, 1, 1)` — a sub-rectangle of the real frustum, not a downscaled full-frame render — renders the picking scene to a 1×1 `WebGLRenderTarget`, reads back that one pixel via `readRenderTargetPixels`, decodes the id, and calls `clearViewOffset()` before returning. This is the exact technique §3.2 specifies ("render instance IDs as colors to an offscreen 1×1 render target at the cursor... GPU picking is O(1)"), and it's the same pattern three.js's own official GPU-picking example uses.
- **Correctness concern worth recording, since it's the kind of thing that silently produces wrong answers instead of an error:** three.js's built-in materials (`MeshBasicMaterial` etc.) bake tone-mapping and linear→output-color-space conversion into their compiled shaders, which would quietly corrupt the exact byte values this technique depends on (e.g. id 42 reads back as some other value entirely). Rather than trust that reasoning alone, read `node_modules/three/src/renderers/webgl/WebGLProgram.js` directly: confirmed the `instanceMatrix`/`instanceColor` attribute declarations and `USE_INSTANCING`/`USE_INSTANCING_COLOR` defines are generated in the shared vertex prefix applied to *any* non-raw material on an `InstancedMesh` (not special-cased to built-in materials), while the tone-mapping and `colorspace_pars_fragment`/`linearToOutputTexel` machinery in the fragment prefix only *defines* helper functions and never calls them unless the material's own `fragmentShader` string references them. `PickingLayer`'s hand-written `THREE.ShaderMaterial` writes `gl_FragColor` directly from the varying with no such call, so it gets instancing support for free with none of the conversion risk. Confirmed from source, not assumed.
- **Hover is rAF-coalesced, click is immediate** (`PickingController.tsx`) — a flood of `pointermove` events collapses to at most one pick per animation frame; a `pointerdown` always runs a fresh pick synchronously, and clicking empty space clears focus. Highlight feedback is two small wireframe sphere markers (hover: white, focus: pink, matching the COVERS edge color) positioned at the picked node — not a change to `ShellInstances`' per-instance colors, same "don't touch the working layer" reasoning as the separate picking scene.
- **Not done yet: focused-subgraph edge highlighting** (dimming every edge except the focused node's 1-hop neighbors) — real UX work, left for a follow-up pass now that picking itself is confirmed.
- **Live interactive confirmation: done, by the project owner, not from this session's tooling** (the Browser-pane tool here still can't composite a frame — same limitation as the renderer spike, below). Hovering correctly reports the node under the cursor; clicking correctly shows the pink focus ring and updates the HUD's Focus row. GPU picking is confirmed correct.
- **Pick latency (90ms) is not representative of the O(1) claim — the test machine has no GPU acceleration at all**, confirmed via `chrome://gpu` showing every category (Canvas, Compositing, OpenGL, Rasterization, WebGL, WebGPU) as "software only," with "Use graphics acceleration when available" already enabled in Chrome's settings — meaning Chrome's own driver-safety check is overriding that setting, not a toggle the user has access to. 90ms lines up with CPU-side vertex transform of ~14k instances (software rendering doesn't benefit from the 1×1-viewport trick the way GPU rendering does, since that trick cuts fragment/rasterization cost, not vertex transform cost — the real bottleneck under software rendering). The *correctness* of the technique is independently confirmed (previous point); its *performance characteristics* need a re-read on real GPU-accelerated hardware before they mean anything. Same caveat applies to every FPS number gathered this session — see 2026-08-28 below, now updated.

## 2026-10-04 — FPS numbers gathered, but invalid: no GPU on the test machine

- **The project owner ran the renderer spike locally and reported real FPS numbers** — single digits to low 30s depending on which of edges/shell-4 were toggled on, worst case (everything on) 5–10fps. On its face this would fail Milestone M2 ("synthetic graph renders at 60fps") badly enough to force the vanilla-Three.js fallback (§1, line 65: "if R3F's abstraction fights you... fall back... decide by end of Sprint 2").
- **Didn't take that at face value, because even the lightest configuration (edges and shell 4 both off — ~8,400 simple opaque unlit spheres, no transparency, no lines) still only hit 9–32fps.** That's far below what *any* GPU-accelerated WebGL implementation should produce for a scene this light — this is a weak result even for a years-old integrated GPU. Asked the owner to check `chrome://gpu`: confirmed every category (Canvas, Compositing, OpenGL, Rasterization, WebGL, WebGPU) reads "software only, hardware acceleration unavailable," with the Chrome setting to enable acceleration already on and the machine not connected to Remote Desktop (both ruled out as explanations) — meaning Chrome's own driver-safety check is force-disabling acceleration regardless of the user-facing toggle.
- **None of this session's FPS or pick-latency numbers are usable for the decision gate.** Software-rendered WebGL would produce roughly the same slow numbers whether the scene is built with react-three-fiber or vanilla Three.js — the bottleneck is the browser's rendering backend, not which JS layer sits on top of it. Making the "commit and don't revisit" R3F-vs-vanilla call off this data would very likely be the wrong call for actual site visitors, essentially all of whom will have real GPU acceleration.
- **Decision gate stays open.** Next step: a reading from a machine/browser with confirmed GPU-accelerated WebGL (`chrome://gpu` showing "Hardware accelerated," not "Software only") — another browser on the same machine, another device entirely, or fixing whatever's blocklisting this machine's current driver. Once that number exists, the R3F-vs-vanilla call gets made and does not get revisited, per the plan's own instruction.

## 2026-08-28 — Sprint 2: renderer spike built, FPS reading needs a human

- **`web/src/scene/` + `web/src/App.tsx`** implement the plan's three required §3.2 techniques against the synthetic 15k-node graph: `ShellInstances.tsx` gives every shell its own `THREE.InstancedMesh` (via drei's `<Instances>/<Instance>`, still exactly one draw call per shell under the hood — nine total, one per shell 0/1/2/2a/2b/3/3a/3b/4), `EdgeLines.tsx` builds a single `LineSegments` buffer for all 31,852 edges with per-vertex color by edge type (COVERS in bright pink, since that cross-shell edge is the actual point of the site), and `OrbitControls` from drei handles camera interaction. `FpsMeter.tsx` samples a rolling FPS average twice a second into an on-page HUD, with checkboxes to toggle edges and the shell-4/personnel layer on and off — useful for comparing the full worst-case stress test against something closer to the production default of edges-hidden-until-focused.
- **Two environment problems fixed along the way, both scoped to dev tooling, neither touching runtime behavior:** (1) `web/vite.config.ts` now points `cacheDir` outside the repo (`os.tmpdir()`) — this repo lives inside a Dropbox-synced folder, and Dropbox was locking `node_modules/.vite` mid-sync (`EBUSY` on the dep-optimizer's rename), breaking `npm run dev` outright. (2) `.claude/launch.json` added so future sessions can `preview_start` the dev server by name instead of re-deriving the npm command each time.
- **Could not obtain a live FPS number from within this session.** The Browser-pane tool used to drive verification reported "the Browser pane is not displayed, so the page is not compositing frames" on every screenshot attempt, across a freshly opened tab and a hard reload alike. Dug into why rather than accepting that at face value: plain DOM layout works fine in this state (`document.body`, `#spike-root`, `#hud` all report correct, real `getBoundingClientRect()` values), but the `<canvas>` element stayed pinned at its raw HTML default (300×150) and react-three-fiber's `<Canvas onCreated>` callback never fired, even after 6+ seconds of polling. `<Canvas>` won't create its `WebGLRenderer` until `react-use-measure`'s `ResizeObserver` reports a real container size, and — unlike basic layout — `ResizeObserver` callback delivery rides the same paint/compositing pipeline that's suspended when a page is never actually displayed. That's a real, structural gap in this session's tooling for this specific job, not a bug in the app: a production build in a real browser gets real compositing and this problem doesn't exist. Deliberately didn't paper over it by bypassing `<Canvas>` for R3F's lower-level imperative `createRoot().configure({ size })` API (which *would* dodge `ResizeObserver` entirely) — that's a permanent structural change to dodge a temporary diagnostic limitation, and it's not how the site's real pages will be built.
- **What's confirmed instead:** clean `tsc -b` typecheck, a dev server that serves with zero console/server errors, and a DOM that correctly reflects the real fetched data (exact node/edge/shell counts render in the HUD) — so the data path and component tree are known-good. What's outstanding is purely the pixels: an actual FPS reading, and the R3F-vs-vanilla-Three.js decision gate that depends on it. **Ask:** run `npm run dev` in `web/` (already has a `.claude/launch.json` entry) and open `http://localhost:5173` in a real browser; the HUD shows node/edge counts and live FPS directly, with edges and the personnel shell toggleable for comparison.

## 2026-08-28 — Sprint 2: synthetic-graph generator for the renderer spike

- **`scripts/generate-synthetic-graph.mjs`**, plain Node (no dependencies) — writes `web/public/data/synthetic-skeleton.json`. Standalone tooling like the Bandcamp harvester, not part of the C# ETL: this is throwaway Space Track scaffolding (§5's parallel-tracks note — Space builds against synthetic data so it never blocks on Data), meant to be replaced by the real build-time JSON export once Sprint 3/4 get there, not a pipeline stage to maintain long-term.
- **Grown bottom-up from cover recordings, not sized top-down.** Each synthetic cover recording either reuses an already-known original recording/release/artist or mints a new one (Zipf-weighted toward established ones), and likewise for its performing band. Every non-core node exists only because some edge pointed at it, so the graph has zero orphan nodes by construction — no separate cleanup pass needed. Verified: every shell's zero-degree count is 0 except shell 0 (the single core node, unlit and unconnected by design per §0).
- **Layout implements §3.1's barycenter heuristic as a single pass, not the full 3–5 iteration version.** Shell 3 (original artists) is positioned in creation order (stand-in for "alphabetical or first-covered date"); shell 2 (covering bands) is ranked by the mean shell-3 position of what its recordings cover; shell 1 (members) is ranked by the mean shell-2 position of their band(s). Each rank maps onto a Fibonacci sphere (golden-angle spiral) per §2.3's full-sphere geometry. One pass already gets most of the "short spokes, not spaghetti" benefit per the plan's own text; further iteration is deferred to the real C# build-time layout, which is where §3.1 says it belongs anyway.
- **Comps (shell 2b) count is hardcoded to 150, not the plan's original "~30" estimate** — the actual Bandcamp harvest (2026-08-25 entry, below) already shows the real series lands around there. Every other shell keeps the plan's §3.2 estimate as its target, scaled to hit the requested total node count.
- **Result at the default 15,000-node target: 14,279 nodes (9 shells), 31,852 edges (2.23/node), 0.64 MB gzipped** — inside §3.2's stated 8k–15k nodes / 30k–60k edges / 1–3 MB gzipped budget. Deterministic for a given `--seed` (mulberry32 PRNG, no `Math.random`), and `--nodes`/`--seed` are exposed specifically so R6's "test with 20k nodes, not 15k" headroom check can reuse this same generator later without new code.
- **Scope stops at the generator.** The renderer spike itself (InstancedMesh + LineSegments + OrbitControls, FPS measurement, the R3F-vs-vanilla-Three.js decision gate) is the next Sprint 2 checklist item and deliberately not started here.

## 2026-08-24 — Airtable base structure (§1.7c)

- **Two bases, not one**, per the plan's own recommendation — keeps Credentials' tiny, near-zero record count from ever being a factor in whether the entity-claims base is near its 1,000-record free-tier cap, and vice versa.
- **`Aliquot Credentials`** — one table, `Credentials` (email, password hash, role: `moderator`/`admin`, created/last-login dates). Stays small forever — only ever as many rows as there are moderators.
- **`Aliquot Claims`** — two tables:
  - `Claims` — one row per claimed/claimable Person or Artist: entity id/type/name, contact email, claim token, issued date, status. This is the one that can grow into the hundreds.
  - `Admin Queue` — the single shared queue for both claim requests and "suggest a new member" submissions (§1.6, §1.7), deliberately one table rather than two review systems. No linked-record field between the two tables — a new-member suggestion has no `Claims` row yet to link to, so both just carry a plain-text Entity ID.
- Base IDs and a Personal Access Token to be recorded in the gitignored `appsettings.Local.json` when the admin app is actually built (Sprint 4) — nothing Airtable-related goes in the repo itself.

## 2026-08-25 — R1 spike resolved: Bandcamp embed IDs + backup files

- **Both R1 questions answered yes**, confirmed against the real catalog (146/146 albums, 0 failures): embed track ids and a real downloadable `mp3-128` file are both sitting in a `data-tralbum` JSON attribute on every album page — no headless browser, no scraping framework, just an HTTP GET and a JSON decode.
- **Album discovery bug, caught and fixed same day:** the first pass scraped only the visible `<a href="/album/...">` links on the landing page — 16 of them — and initially reported that as the whole catalog. It wasn't; the other 130 albums (back to July 2014) live in a `data-client-items` JSON blob on `/music` that Bandcamp's own JS uses for lazy-loading the discography grid, invisible to a plain link scrape. Fixed by reading `/music` and merging both sources. Worth remembering: **a link-only scrape can look complete and be wrong by an order of magnitude** — always cross-check a scraped count against an independent expectation (here, the user's own "~150 once finished").
- **PowerShell, not the C# ETL, for this harvester** (`scripts/harvest-bandcamp.ps1`) — it's a standalone, resumable, long-running (hours, by design) crawl with a deliberately slow random delay between albums (60-600s) to stay well clear of anything that looks like hammering the site. Keeping it separate from the C# ETL app means the ETL's own MusicBrainz/Discogs runs (§4, seconds-to-minutes) aren't coupled to a process that's meant to run for hours in the background. The ETL can ingest `etl/.cache/bandcamp/*.json` as a normal cached input once this has run.
- **Bandcamp's `robots.txt` disallows `ClaudeBot` site-wide.** Noted explicitly in the script's own help text and in `docs/RUNBOOK.md`: this script is meant to be *run by the project owner*, under the project's own identity, not fetched by an AI agent on the owner's behalf. The paths it touches (landing page, `/album/`) are allowed for generic crawlers regardless.
- **Signed download URLs expire ~24h after the page fetch.** This matters for §1.9's backup-tier population later in the plan — harvesting metadata and harvesting the actual audio bytes can't be arbitrarily far apart in time.
- Full harvest completed same day: **146/146 albums, 3,830 tracks, 0 failures.**

## 2026-08-25 — Sprint 2: Bandcamp normalization into SQLite

- **Raw staging tables, separate from normalized tables** (`bandcamp_album_raw`, `bandcamp_track_raw`) — the plan's own Sprint 2 instruction ("land what Bandcamp gives you raw in SQLite, untransformed"). Reasoning beyond just following instructions: `etl/.cache/*` is gitignored, but `aliquot.sqlite` is committed (§8) — landing the raw JSON in SQLite means a fresh clone of the repo still has the full Bandcamp harvest without re-running a multi-hour scrape.
- **`Aliquot.Etl.Bandcamp.BandcampImporter`** reads the raw tables' in-memory source and upserts into `release` (cover), `recording` (cover), `artist` (role `covering`), `appears_on`. Idempotent by construction — every write is `ON CONFLICT DO UPDATE` or `INSERT OR IGNORE`, verified by running the importer twice back-to-back with identical output counts.
- **Added `performed_by` (Artist → Recording) as an 8th edge**, beyond §2.2's formal 7. The formal model only has performance at the Person level (`PERFORMED_ON`, reachable via `MEMBER_OF`), but Sprint 2 has no person-level roster yet — that's Sprint 3 — while §2.3 needs cover recordings clustered around their covering artist for Shell 2a *now*, and Bandcamp's track data already names the performing artist directly. Documented in `Schema.sql` itself so the deviation from §2.2 is explained where anyone reading the schema will actually see it. Not meant to be superseded once `PERFORMED_ON` exists later — it stays as the direct, always-available fallback.
- **Entity ID scheme:** `release/bandcamp/{album_id}`, `recording/bandcamp/{track_id}`, `artist/bandcamp/{slugified-name}` — deterministic and stable across re-imports. **Known limitation:** artist identity is exact-string-match on Bandcamp's free-text `artist` field per track, with no dedup beyond that. Two spellings of the same real band (typo, capitalization drift over 12 years, "The X" vs "X") will currently produce two separate `artist` rows. This is exactly the kind of thing Sprint 3's manual roster-resolution pass (already budgeted in the plan, R3) needs to catch — not fixed now.
- **`slug` deliberately left null** on every normalized row — §1.8 assigns Person/covering-Artist slugs in Sprint 3 and Recording/Release slugs in Sprint 4. Populating it now would be premature and out of sequence with the plan.
- Added `recording.duration_seconds` to the schema (not in §2.1's original field list, but Bandcamp gives real duration data and it's obviously needed for audio UI later) and a header-comment note that the schema now has 8 edges, not 7.
- **Verified end to end:** 146 releases, 3,830 recordings, 1,249 distinct covering artists, 3,830 `appears_on` + 3,830 `performed_by` edges. Spot-checked for artist-name corruption (a `Oms en série` entry initially looked mangled — turned out to be a Windows console encoding artifact in a debug script, not real data corruption; the stored UTF-8 bytes are correct).
